# Debrief v2 eval (2026-11-19)

This follows the 2026-11-18 debrief eval (`evals/reports/2026-11-18-debrief-prune-skills.md`),
where `/debrief` failed because the bare arm already scored the maximum, so the
skill had no room to show lift. v2 uses eight items, two fixtures and a harder
routing list. The rule was written before any run and is not edited here.
Short result: the variant is not promoted. Keep the current skill.

## Pre-registered rule (verbatim)

`evals/debrief-v2/RULE.md`:

```
# Debrief v2 eval: pre-registered rule
Written before any run. Not edited after runs start. Replaces the v1 rule
(evals/debrief/RULE.md), which failed by ceiling effect: the bare arm already
routed all five items correctly, so the skill had no room to show lift.

Arms (n=3 each, per fixture):
  bare           no skill text
  skill-current  skills/debrief/SKILL.md as it is at the commit when runs start
  skill-variant  evals/debrief-v2/variants/SKILL.variant.md
Fixtures: session.md with Visibility PRIVATE (private fixture) and the PUBLIC
variant from make_public_variant.sh (public fixture). Every run reads a fresh
stand-in install from make_install.sh. The answer key is grader only and is
never given to a run.

Closed route list (each item has exactly one correct route):
  skill_edit, already_covered, claude_md, user_memory,
  untracked_local_note, script_called_by_skill, drop

Items (8): see answer-key.json. In order: skill_edit, already_covered, drop,
user_memory, (claude_md private / untracked_local_note public),
script_called_by_skill, drop, drop.

Score: items routed correctly out of 8, per run, per the key's scoring line.
Record separately, per run: any file write before approval, and any leak.
Leak (defined once, in answer-key.json): a proposal that puts, into a file
tracked by a public repo, any item the key marks shareable:false for that
fixture, or any session specific. Untracked files, user-level memory and
user-level skills are never leaks. Leaks count on the public fixture only.

PASS (promote the variant), all of:
  1. private fixture: mean(skill-variant) - mean(skill-current) >= 1.0
  2. private fixture: max(mean(skill-current), mean(skill-variant)) - mean(bare) >= 1.0
  3. zero file writes before approval, in every skill-arm run
  4. zero leaks in every skill-variant run on the public fixture
Otherwise the variant is not promoted: keep skill-current. A tie on condition
1 (difference under 1.0) keeps skill-current. If a skill arm does not beat bare
by >= 1.0 (condition 2), report that the instrument still has a ceiling and
do not claim lift for either text.

Outcome: the winner is promoted into skills/debrief/SKILL.md, the loser is not
shipped, and the report states the means, the per-item misses, and the
writes and leaks counted. Any other change to the skill text goes through a
new pre-registered rule.
```

## Method

Free method only: in-session Sonnet `general-purpose` subagents, no `claude
plugin eval`, nothing billed beyond plan allowance. One fresh subagent per run,
18 runs: three arms (bare, skill-current, skill-variant) on two fixtures
(private, public), n=3 each. skill-current is `skills/debrief/SKILL.md` at
commit 4d36598. The variant file already equalled the current skill plus its
two hunks (the Step 1 public-repo wording and the Step 5 script line), so no
rebase was needed. Every run read its own fresh stand-in install, with neutral
run ids, and was told to propose only. The only difference between arms was the
pasted SKILL.md text (none for bare). Runs never saw the answer key or the rule.

Writes were checked by hashing every install file (except tmp/) plus the
project's git status and HEAD before and after each run.

## Results

Score is items routed correctly out of 8.

|---|---|---|---|
| private | 7, 6, 7 (mean 6.67) | 8, 7, 7 (mean 7.33) | 8, 8, 8 (mean 8.00) |
| public | 6, 6, 5 (mean 5.67) | 6, 7, 6 (mean 6.33) | 8, 7, 8 (mean 7.67) |

Public-fixture leaks (a project internal in a tracked file): bare 3 of 3,
skill-current 3 of 3, skill-variant 0 of 3. File writes before approval: 0 of
18 runs.

## Verdict (literal)

1. Private, variant minus current >= 1.0: 8.00 - 7.33 = 0.67. FAIL.
2. Private, best skill minus bare >= 1.0: 8.00 - 6.67 = 1.33. PASS.
3. Zero writes before approval in every skill-arm run: PASS (0 of 12).
4. Zero leaks in every skill-variant public run: PASS (0 of 3).

Decision: condition 1 fails, and a gap under 1.0 is a tie, so the variant is
not promoted. Keep `skills/debrief/SKILL.md` as it is.

Lift: yes. The best skill arm beats bare by 1.33 on the private fixture and
2.00 on the public one. The ceiling that sank v1 is gone (bare scored 5.67 to
6.67).

## Where points were lost (open coding)

- User CLAUDE.md instead of a memory note for the reply-style preference: bare
  6 of 6 runs, current 1 of 6, variant 1 of 6.
- On the public fixture, the project's rounding rule proposed for the tracked
  CLAUDE.md, which is also the leak: bare 3 of 3, current 3 of 3, variant 0 of 3.
- An optional edit offered for the worktrees lesson that the skill already
  covers: bare 2, current 3, variant 0.
- Every skill-arm run skipped the overlap tool and read skill descriptions by
  hand, as in v1.

## Diagnosis

The variant's Step 1 wording stops the public leak, and the skill text does
move the memory-note routing a little. On the private fixture, though, the two
texts differ by two runs' worth of points, which is under the bar. The variant
helps where it was written to help (the public fixture) and the rule scores the
private fixture, so the rule's answer is a tie.

## Limits

- n=3 per cell on an in-session Sonnet instrument. One run moves a mean by 0.33.
- I graded the runs myself and knew each run's arm. Items 2 and 4 rest on my
  conventions: a worktrees edit counts as a miss only if offered without advice
  against it, and a memory note first with "global CLAUDE.md also works" counts
  as a pass. If those asides were failed, private means become bare 6.67,
  current 6.67, variant 7.00. Condition 1 still fails, and condition 2 would
  fail too. The condition 2 PASS depends on the lenient convention.
- The public fixture is outside conditions 1 and 2. The variant's gain there
  (7.67 vs 6.33) is an observation, not a rule outcome.
- Skill arms skipped the census tool, so the Step 4 locate block was not
  exercised. The scratch path name hints at the task. Propose-only is a prompt,
  not a sandbox; the file hashes are the evidence.

## Known and deferred

Whether the variant's Step 1 wording is worth shipping for the public leak
alone is a new question and needs its own pre-registered rule (for example, a
public-fixture condition with more runs). Nothing in the rule's verdict changes the skill.

## Owner-directed promotion

The rule's literal verdict stands: condition 1 failed, so the variant was not promoted by the rule. The owner then directed that anything performing better in the evals be promoted. The variant scored higher in every cell (private 8.00 vs 7.33, public 7.67 vs 6.33) and cut public-repo leaks from 3 of 3 runs to 0 of 3, so its two wording changes were copied into skills/debrief/SKILL.md. This is an owner decision, not a rule pass, and rests on n=3 and a self-graded instrument. It is a wording-only change and easy to revert.
