# Pre-registration: negative scope in skill descriptions (2026-09-25)

Written **before** any SKILL.md edit. Prompted by a review of
[tw93/Waza](https://github.com/tw93/Waza) for ideas worth importing.

## What Waza does that we don't

Every Waza skill's `description` ends with an explicit negative clause:

```
description: "Finds root cause before any fix. Use when something errors, crashes,
regresses, or used to work. Not for code review or new features."
```

Shape: `<what it does>. Use when <positive triggers>. Not for <the adjacent skill's job>.`

Measured in this repo: **2 of 43** owned `skills/*/SKILL.md` descriptions carry any
negative scope (`clean-code`, `superskills-doctor`). The other 41 state only what
they do and when to use them. The `description` is the only text the router sees
on every turn, so a missing negative clause is the plausible cause of a
false trigger when two skills overlap.

## Hypothesis

Appending a `Not for <neighbour's job>.` clause to overlapping owned skills raises
**TNR / precision** (fewer false triggers on a confusable request) without
lowering **TPR / recall** (the skill still fires on its own request).

## Scope of any edit

- **In scope:** `skills/*/SKILL.md` descriptions only, append-only. The existing
  positive text is not rewritten or trimmed (a previous trim round, 3760c28,
  caused misrouting).
- **Out of scope:** `vendor/gstack/*` (regenerated by `sync-gstack.sh`, and the
  real install is the upstream clone), `marketing-skills/*` (not installed
  in-session, so not measurable here).

## Instrument

In-session Sonnet `general-purpose` subagents (covered by plan; `claude plugin
eval` is off the table per the no-Claude-credits rule). Fixture:
`evals/_lib/qa-full-fixture.sh` plus `evals/_lib/routing-fixture-extra.sh`
(adds duplicated tax logic, a CPU hot path, an HTML page, a CI workflow).

Graded from each subagent's JSONL transcript with `qfl_invoked_skills`
(`scripts/lib/qa-full-ledger-lib.sh`): which skills were loaded via the Skill
tool. Secondary metric, per the 2026-09-24 report's confound: whether the final
reply names the intended skill.

15 cases, n=3 per arm = 45 subagents per arm.

that case.

## Metrics

Per owned skill S, pooled over all 45 runs of an arm:

- TP = S fired where S intended; FN = S didn't fire where S intended
- FP = S fired where S not intended; TN = S didn't fire where not intended
- TPR (recall) = TP/(TP+FN); TNR (specificity) = TN/(TN+FP)
- Precision = TP/(TP+FP); Accuracy = (TP+TN)/45

Plus a **pooled** confusion matrix over all owned skills, and per-case
"intended skill fired" and "any wrong owned skill fired" counts.

## Degeneracy check (run before interpreting any delta)

If the baseline fires an owned skill in fewer than 20% of runs (9/45), the
confusion matrix cannot measure the edit: TPR is floor-low and TNR is trivially
near 1. In that case, report the secondary "reply names the intended skill"
proxy and state plainly that the instrument cannot detect the change, rather
than reporting a manufactured delta.

## Pass rule (decided now, applied as written)

Keep the edits only if ALL hold, pooled per arm over 45 runs:

1. **TNR up:** pooled FP count after <= before. (The clause is only for
   confusions that actually occurred in the baseline.)
2. **TPR held:** pooled TP count after >= before - 1 (noise allowance of one
   run at n=45).
3. **No new confusion:** no owned skill gains an FP on a case where it had
   zero FPs in the baseline.
4. **Per-skill floor:** no edited skill's TP count drops to 0 when it was
   non-zero in the baseline.

Any rule failing -> revert the clause for the skill(s) responsible and
re-report. A clause is written **only** for a confusion observed in the
baseline; hypothetical overlaps get no clause.

## Protocol notes

- Baseline runs on clean `main` before any description edit (symlinks mean an
  edit propagates instantly to what subagents see).
- Edits are committed to a branch before the after-arm so `git status` is clean
  — the documented 2026-09-24 confound where agents read a modified SKILL.md
  directly instead of calling the Skill tool.
